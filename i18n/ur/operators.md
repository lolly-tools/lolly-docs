# آپریٹرز کے لیے Lolly

### ایک تہہ در تہہ (defence-in-depth) سیکیورٹی اور انٹیلی جنس حکمت عملی - جو محض ایک تخلیقی پروڈکشن پلیٹ فارم بھی ہے

وہ زیرو-ٹرسٹ تنظیمی مدافعتی نظام جو آپ کے پہلے سے کیے جانے والے کام کے گرد لپٹتا ہے - تاکہ آپ کی ٹیموں کو روزانہ درکار معمول کا تخلیقی کام آپ کے دائرے سے باہر رِسنے کے بجائے اس کے *اندر* ہو۔

**اس میں آپ کے لیے کیا ہے۔** آپ وہ شخص بن جاتے ہیں جس نے کسی ایسی چیز کو ہاں کہی جو محفوظ *اور* مقبول دونوں ہے۔ آپ ایک ایکسفلٹریشن سوراخ بند کرتے ہیں، صلاحیت حاصل کرتے ہیں اور ایک ہی حرکت میں درخواستوں کی قطار مٹا دیتے ہیں - وہ نادر سیکیورٹی جیت جو آپ کو کم نہیں بلکہ زیادہ پسندیدہ بناتی ہے۔ قانونی ٹیم کی طرف سے رات 3 بجے کوئی کال نہیں کیونکہ ممنوعہ فائلیں یا کسٹمر ڈیٹا کسی بے ترتیب ویب ٹول تک نہیں پہنچے؛ آپ کے سامنے کم SaaS وینڈرز، معاہدے اور آڈٹس؛ اور ایک مکمل طور پر دوبارہ قابلِ تخلیق آڈٹ ٹریل جس کی طرف آپ کوئی پوچھے تو اشارہ کر سکیں۔ آپ زیادہ سکون سے سوتے ہیں، اور یہ کرتے ہوئے چند دن روشن بھی کرتے ہیں۔

Lolly کوئی دوسرے درجے کا تخلیقی ٹول نہیں ہے: یہ ہر ایک کے ہاتھ میں پروڈکشن معیار کا آؤٹ پٹ دیتا ہے، اور برانڈ کی رہنمائی میں تخلیق کا تجربہ بے مثال ہے۔ اسے بڑے پیمانے پر تقسیم کرنا *محفوظ* ہونے کی وجہ ساختیاتی ہے: کچھ بھی اپ لوڈ نہیں ہوتا جو آپ نے وہاں نہیں رکھا، ہر نتیجہ دوبارہ قابلِ تخلیق ہے اور ہر ایکسپورٹ صنعت کے صف اول کے کرپٹوگرافک ریکارڈز کی متعدد تہیں لے جا سکتا ہے۔ کوئی دستاویز آپ کی میز تک کیسے بھی پہنچی ہو، آپ اس کی مکمل پروونینس دیکھ سکتے ہیں، آیا اس کے ساتھ چھیڑ چھاڑ ہوئی ہے، اور آیا آپ اسے پکسل-پرفیکٹ دوبارہ تخلیق کر سکتے ہیں۔

> **موجودہ صورتحال۔** Lolly کی سیکیورٹی خصوصیات بذاتِ خود مضبوط ہیں، اور اس کے cryptography اور file-parsing engines SUSE کی enterprise-grade infrastructure hardening سے گزر رہے ہیں۔ نیچے دیے گئے seals، on-device signing اور encryption ابھی حقیقی اور قابلِ دفاع ہیں، اور آزاد سرٹیفیکیشن کی جانب پختہ ہو رہے ہیں - اس لیے جہاں کوئی معاہدہ certified اعتماد کا تقاضا کرے، وہاں انہیں defence-in-depth کے طور پر deploy کریں جب تک یہ عمل مکمل نہیں ہوتا۔

## اسٹریٹجک فائدہ

معمول کا تخلیقی کام عام طور پر جس طریقے سے ہوتا ہے وہ ایک ذمہ داری کی سطح ہے: فائلیں بیرونی ڈیزائن ٹھیکیداروں کو ای میل کی جاتی ہیں، برانڈ اثاثے درجن بھر SaaS ایڈیٹرز میں اپ لوڈ ہوتے ہیں، کسٹمر ڈیٹا کسی اجنبی کے ویب ٹول میں محض "ایک فوری گرافک بنانے" کے لیے پیسٹ کیا جاتا ہے۔ ان میں سے ہر ایک ڈیٹا آپ کے کنٹرول سے نکل رہا ہے۔

Lolly اسے الٹ دیتا ہے۔ وہ کام جو ان لیکس کا *سبب* بنتا تھا - اقتباس کارڈ، مقامی بنایا گیا بینر، ایونٹ بیج، ریڈیکٹڈ اسکرین شاٹ - اب ایک ایسے ٹول پر ہوتا ہے جو ملازم کی اپنی ڈیوائس پر، آپ کے برانڈ کے خلاف، بغیر کسی سرور کے چلتا ہے۔ آپ نے کسی خطرناک ورک فلو کے اوپر کوئی کنٹرول شامل نہیں کیا؛ آپ نے خطرناک ورک فلو کو ایسے ورک فلو سے بدل دیا جس میں شروع سے ہی کوئی ایکسفلٹریشن راستہ موجود نہیں۔

- **Configuration آپ کی ہے۔** Engine اور shells اوپن سورس ہیں (MPL-2.0)۔ اپنا auth، telemetry یا CA اوورلے کریں؛ خود host کریں یا نہ کریں؛ آپ کے پاس فیچرز اور لاگت پر مکمل کنٹرول ہے، git-tracked، کسی SaaS database میں بند نہیں۔
- **حکمرانی dashboard نہیں، ڈیٹا ہو سکتی ہے۔** جب آپ کو یہ کنٹرول چاہیے، tool کیٹلاگ کو ایک Git repository کے طور پر منظم کریں - pull-request کا جائزہ برانڈ کی منظوری بن جاتا ہے، مکمل audit trail اور آپ کے workforce کے چھوئے ہر template کی فوری rollback کے ساتھ۔ یہ ایک اختیار ہے، فرض نہیں، اور یہ عین ایک ہی میز سے تعلق رکھتا ہے: creators مکمل طور پر ایپ کے اندر کام کرتے ہیں، جو بناتے ہیں اسے ایک **session** کے طور پر محفوظ کرتے اور share link، backup یا لائیو collaboration کے طور پر آگے بڑھاتے ہیں - ان میں سے کسی کو بھی git کی ضرورت نہیں۔ جب ان میں سے کوئی سیشن ایک مستقل نقطۂ آغاز بننے کا مستحق ہو، جو بھی deployment چلاتا ہے وہ لنک کھولتا ہے، اس کی قدروں کو brand pack میں اس tool پر ایک **template** کے طور پر ریکارڈ کرتا ہے اور commit کرتا ہے۔ اس کے بعد سے یہ tool کے "New from template" چوزر میں ظاہر ہوتا ہے اور `?template=<id>` کے طور پر deep-linkable ہوتا ہے۔ Git admin کا locking قدم ہے، ایک بار استعمال ہوتا ہے، اور کبھی وہ چیز نہیں جسے کسی creator کو چھونا پڑے۔ دیکھیں [اپنانا اور حکمرانی](/info/adoption-governance.html)۔
- **حفاظتی رکاوٹیں ساختی ہیں۔** برانڈ کی پابندیاں templates میں hard-coded ہیں، رہنما اصولوں کے طور پر شائع نہیں کی گئیں جنہیں لوگ نظرانداز کر سکیں۔ غلط نتیجہ محض حوصلہ شکنی کا شکار نہیں ہوتا - وہ سرے سے ناقابلِ نمائندگی ہوتا ہے۔

> **آپ پوری زنجیرِ عمل کو کنٹرول کرتے ہیں۔** ایک تخلیق کار قواعد وضع کرتا ہے اور ایک ڈیویلپر انہیں وسعت دیتا ہے، مگر یہ آپریٹر ہی ہے جو اس لائف سائیکل کو پوری تنظیم میں چلانے کے لیے محفوظ بناتا ہے - وہی ٹول جو ایک نمائندے کو ہوائی جہاز میں خود خدمت کرنے دیتا ہے وہی ہے جسے آپ Git ریویو کے ذریعے گیٹ کر سکتے ہیں، اپنے MDM کے ذریعے ڈیپلائے کر سکتے ہیں اور کرپٹوگرافک طور پر تصدیق کر سکتے ہیں۔ دیکھیں کہ کردار کیسے مل کر اثر بڑھاتے ہیں [ایک مہم کا لائف سائیکل](/info/overview.html#the-lifecycle-of-a-campaign) میں، اور آپ اسے کیسے منظم کرتے ہیں [اپنانا اور گورننس](/info/adoption-governance.html) میں۔

## مواد میں اضافہ کرتے ہوئے درخواستوں کی قطار مٹا دیں۔

Lolly کا ایک مقصد **ڈیزائن-درخواست کا انحراف (deflection)** ہے: معمول کی درخواستیں جنہیں کبھی ڈیزائنر تک پہنچنے کی ضرورت نہیں پڑتی کیونکہ جس شخص کو اثاثے کی ضرورت تھی اس نے خود، درست طریقے سے، منٹوں میں اسے بنا لیا۔ ہر منحرف شدہ ٹکٹ بیک وقت پیداواریت کی جیت ہے اور ایک کم فائل جو ہاتھوں سے گزرتی ہے۔

Lolly اس طرح بنایا گیا ہے کہ آپ کی تنظیم واقعی جیسے کام کرتی ہے اس میں فٹ ہو - اسے ڈیپلائے کرنے کا کوئی ایک ہی درست طریقہ نہیں ہے:

- **ڈیپلائے کریں، سرو نہ کریں۔** Lolly کو اپنے موجودہ MDM (Intune، Jamf، Munki…) کے ذریعے ڈیوائسز تک پہنچائیں۔ یہ مقامی طور پر بطور ڈیسک ٹاپ/موبائل ایپ یا آف لائن PWA چلتا ہے - کسی بھی فائر وال کے پیچھے، کسی بھی ایئر-گیپڈ ماحول میں کام کرتا ہے، کسی سرور کو برقرار رکھنے کی ضرورت نہیں اور IT اپ ڈیٹ کی رفتار پر کنٹرول رکھتا ہے۔
- **صرف سرو کریں۔** اپنے نیٹ ورک کے اندر (یا VPN کے پیچھے) ایک انسٹینس چلائیں؛ صارفین اسے براؤزر میں رسائی دیتے ہیں، کچھ بھی انسٹال نہیں ہوتا۔ ایک ٹول ایک بار شائع کریں، ہر کسی کے پاس فوراً موجود ہو جاتا ہے؛ رسائی کنٹرول کے لیے اپنے IdP کے ساتھ جوڑیں۔
- **ہائبرڈ۔** آف لائن فیلڈ ورک کے لیے مقامی ایپس، ادھار لی گئی مشینوں کے لیے ہمیشہ تازہ ترین براؤزر ورژن - دونوں ایک ہی ٹول لائبریری کی طرف اشارہ کرتے ہیں۔

مکمل ڈیپلائے ماڈلز اور انتظامی واک تھرو [ڈیپلائمنٹ](/info/deployment.html) اور [کنفیگریشن](/info/configuration.html) میں موجود ہیں۔

## اینٹی-ایکسفلٹریشن یوٹیلیٹیز

Lolly ٹولز کی ایک قسم - پرائیویسی یوٹیلیٹیز - *خاص طور پر* فائلوں کو دائرے کے اندر رکھنے کے لیے موجود ہے۔


- **پوشیدہ ڈیٹا ہٹائیں (Strip hidden data)**
 دستاویزات اور میڈیا فائلوں سے مقام اور تمام پوشیدہ شناختی معلومات ہٹائیں۔

- **Text Helper**  
ساخت یافتہ اور غیر ساخت یافتہ متن کو گمنام بنائیں، ان کوڈ کریں، فارمیٹ کریں اور تبدیل کریں۔ 

- **Compress PDF**
ڈیوائس پر ہی ایک بڑی PDF کا حجم کم کریں، تاکہ جیسے ہی کوئی فائل ای میل کے لیے بہت بڑی ہو، کوئی بھی تیسرے فریق کی "میری PDF کمپریس کریں" ویب سائٹ کا رخ نہ کرے - جو کہ بالکل وہی جگہ ہے جہاں سے ڈیٹا نکل جاتا ہے۔ 

یہ سب ڈیوائس پر ہونے والی تبدیلیاں ہیں: آپ کی فائل یا ڈیٹا اندر جاتا ہے، صاف بائٹس باہر آتے ہیں اور **اپ لوڈ کرنے کے لیے کوئی سرور نہیں ہوتا**۔ یہ اس عام "صاف کرنے کے لیے اپنی فائل کسی اجنبی کی ویب سائٹ پر اپ لوڈ کریں" والے ٹول کے بالکل الٹ ہیں، جسے ایک نیک نیت ملازم بصورتِ دیگر استعمال کرتا ہے۔

## قطعیت اور تکرارپذیری

ہر ٹول ان پٹ ایک URL پیرامیٹر کے طور پر ظاہر کیا جا سکتا ہے، اور وہی ان پٹس ہمیشہ وہی فائل پیدا کرتے ہیں۔ اس کے آپریٹر کے لیے دو نتائج ہیں:

- **URL ہی اثاثہ ہے۔** لنک کمٹ کریں، اثاثہ حسبِ ضرورت دوبارہ تخلیق کریں - Git میں کوئی بائنری چیک ان نہیں ہوتی، چیٹ میں "تازہ ترین ورژن" ڈھونڈنے کی ضرورت نہیں۔ اثاثے اور ٹول کی IDs مستقل معاہدے ہیں، لہٰذا آج بنایا گیا لنک بعد میں بھی درست حل ہوگا۔
- **CLI وہی رینڈر پاتھ ہے** جو GUI کا ہے، لہٰذا بلڈ پائپ لائنز اور ایپ کبھی الگ نہیں ہوتے۔ OG امیجز، سوشل کارڈز اور ڈیٹا ویژولز بلڈ کے وقت، تکراری طور پر تخلیق کریں۔

Prompt to Image قطعیت کی سب سے سادہ مثال ہے: متن ہی پورا ان پٹ ہے، ٹائپ سیٹ شدہ تصویر ہی پورا آؤٹ پٹ ہے اور وہی متن ہمیشہ اسی طرح سیٹ ہوتا ہے۔

ایکسپورٹس **Content Credentials** رکھ سکتے ہیں - ایک دستخط شدہ [C2PA](https://c2pa.org) مینی فیسٹ جو فائل کے بائٹس کے ایک ہیش سے منسلک ہوتا ہے۔ فائل میں بعد کی کوئی بھی تبدیلی مہر توڑ دیتی ہے، لہٰذا C2PA سے واقف ایک تصدیق کنندہ **آف لائن، خالص ریاضیاتی طور پر تبدیلی کا پتا لگاتا ہے**۔ یہ اسناد چھیڑ چھاڑ کا *پتا دینے والی* ہیں: یہ چھیڑ چھاڑ کو روکنے کی بجائے اس کی نشاندہی کرتی ہیں، اور یہی وہ بات ہے جو مکمل آف لائن تصدیق کو ممکن بناتی ہے۔

- **پہلے سے فعال، ڈیوائس پر۔** دستخطی کلید ڈیوائس پر تخلیق ہوتی ہے، ناقابلِ استخراج ہے (خود Lolly بھی اسے نہیں پڑھ سکتا) اور دستخط مقامی طور پر ہوتے ہیں - صرف اختیاری شناختی *اندراج* ہی کبھی نیٹ ورک سے رابطہ کرتا ہے۔
- **اعتماد کے درجے۔** غیر اندراج شدہ ایکسپورٹ درست ساخت کا حامل مگر گمنام دستخط شدہ ہوتا ہے (`untrusted`)۔ ایک **تصدیق شدہ شناخت** درج کروائیں (Lolly CA سے مختصر مدت کا سرٹیفکیٹ، ایک ای میل سے منسلک) تو Lolly root پن کرنے والے تصدیق کنندگان `trusted` + دستخط کنندہ کی ای میل رپورٹ کرتے ہیں۔ ایک قابلِ اعتماد ٹائم اسٹیمپ اتھارٹی اور تیسرے فریق کے تصدیق کنندہ کا سبز نشان (C2PA مطابقت) روڈ میپ پر ہیں۔ ہر درجہ واضح ہے، اور کوئی فائل صرف وہی اعتماد دعویٰ کرتی ہے جو ثابت کر سکتی ہے۔
- **اسناد کی مدت** دستخط کے وقت آپریٹر/صارف کا فیصلہ ہے: 7 / 30 / 90 / 365 دن، ڈیفالٹ 30۔
- **The Lolly Imprint۔** ایک دوسرا، تکمیلی سگنل جو **پہلے سے فعال** ہے: ایک غیر مرئی پکسل واٹرمارک جو ریسٹر ایکسپورٹس میں (اور PDF/PPTX کے اندر Lolly سے رینڈر کیے گئے ریسٹرز میں، کبھی صارف کی اپنی سرایت شدہ تصویر میں نہیں) پکایا جاتا ہے۔ جہاں اسناد کسی بھی کنٹینر تبدیلی پر ختم ہو جاتی ہیں، Imprint دوبارہ محفوظ کرنے یا اسکرین شاٹ سے بچ جاتا ہے - ایک پائیدار "یہ پکسلز Lolly سے گزرے" اشارہ، صرف موجودگی کا، کوئی ذاتی ڈیٹا نہیں۔ یہ ایک سخت دفاع نہیں بلکہ ابہام کے ذریعے سیکیورٹی ہے، اور اسناد کی جگہ لینے کی بجائے اس کی تکمیل کرتا ہے۔ `imprint=0` اس سے دستبرداری کرتا ہے۔
- **پائیدار Content Credentials (اختیاری)۔** ایک ریسٹر ایکسپورٹ اضافی طور پر ایک غیر مرئی *پائیدار* نشان لے جا سکتا ہے جو ایک نرم پابند شناخت کنندہ کو انکوڈ کرتا ہے، تاکہ C2PA اسناد اس کیس میں بھی بازیافت ہو سکیں جہاں کسی سوشل اپ لوڈ یا دوبارہ محفوظ کرنے نے فائل کا میٹا ڈیٹا ہٹا دیا ہو - وہ صورت جہاں ایک عام اسناد ضائع ہو جاتی۔ یہ صرف ریسٹر کے لیے ہے اور ایک نیورل انکوڈ پاس کی قیمت رکھتا ہے، لہٰذا یہ ڈیفالٹ کے طور پر بند ہے (فعال کرنے کے لیے `durable=1`)۔ Lolly آج `/verify` پر اپنے پائیدار نشان کو آف لائن پہچانتا ہے؛ تیسرے فریق کے ٹولز (مثلاً Adobe) کے ذریعے بازیافت صنعتی نرم پابندی کے حل کے قائم ہونے کے بعد ممکن ہوگی۔
- **تصدیق ڈیوائس پر ہوتی ہے۔** کوئی بھی فائل `/verify` پر (یا `lolly validate <file>`) ڈراپ کریں تاکہ یہ آف لائن رپورٹ ملے کہ آیا یہ واقعی Lolly سے بنائی گئی تھی اور اس کے بعد سے تبدیل نہیں ہوئی۔ ویب Verify ویو AI سے تخلیق کردہ مواد کی بھی نشاندہی کرتا ہے، Lolly Imprint کا پتا لگاتا ہے، **SEAL** دستخطوں کی تصدیق کرتا ہے (ایک بائٹ سطح کا دستخط - صفر نیٹ ورک درخواستوں کے ساتھ: انجن ایک *انجیکٹ شدہ* DNS کلید ریزولور لیتا ہے اور آج کوئی بھی شیل ایسا انجیکٹ نہیں کرتا، لہٰذا اپنی ان لائن `pk=` کلید رکھنے والا ریکارڈ مکمل طور پر آف لائن تصدیق ہو جاتا ہے جبکہ DNS-کلیدی ریکارڈ باہر رابطہ کرنے کی بجائے "no key resolver and no inline key" رپورٹ کرتا ہے - `engine/src/seal.ts` میں `SealPublicKeyResolver` دیکھیں)، اختیاری طور پر تیسرے فریق کے پکسل واٹرمارکس کے لیے گہرا اسکین کرتا ہے (ایک بار کی ڈیوائس پر ماڈل ڈاؤن لوڈ) اور پوشیدہ ڈیٹا سامنے لاتا ہے - یہ سب کچھ فائل اپ لوڈ کیے بغیر۔ دیکھیں [Content Credentials Identity](/info/content-credentials-identity.html)۔

> **باہمی تعامل کے نوٹس۔** Lolly آج آف لائن اپنی اسناد اور بہت سے تیسرے فریق کی اسناد کی تصدیق کرتا ہے، بشمول دیگر پروڈیوسرز کے C2PA claim **v2** مینی فیسٹس پڑھنا۔ دو کنٹینرز ابھی زیرِ تکمیل ہیں، دونوں اس لیے کہ C2PA کے پاس ان کے لیے ابھی تک کوئی معیاری میپنگ نہیں، لہٰذا Lolly اسناد کو اپنی ایک جگہ پر رکھتا ہے اور Lolly کا تصدیق کنندہ ہی وہ ہے جو اسے واپس پڑھتا ہے: **WebM** (مینی فیسٹ ایک Matroska اٹیچمنٹ کے طور پر سفر کرتا ہے) اور **Ogg/Opus** (OpusTags کمنٹ ہیڈر میں ایک `C2PA=` فیلڈ، اس بائٹ رینج کے پابندی سے خارج ہونے کے ساتھ تاکہ آڈیو ابھی بھی یکساں طور پر ہیش ہو)۔ باقی سب کچھ معیار کے مطابق مہر بند ہوتا ہے - تیسرے فریق کے ٹولز Lolly کی MP4، M4A، MP3، WAV، PNG، JPEG اور PDF کو بغیر کسی اضافی کام کے تصدیق کرتے ہیں۔ دونوں میپنگز کے لیے `engine/src/c2pa-containers.ts` دیکھیں؛ معیار طے پا جانے پر یہ اس کے ساتھ یکجا ہو جائیں گی۔

## خفیہ کاری اور پاس ورڈ

ان فائلوں کے لیے جنہیں مقفل سفر کرنا ضروری ہو، سب کچھ ڈیوائس پر ہی ہوتا ہے:

![ایکسپورٹ پینل میں لاک کارڈ: ایک پاس ورڈ، اور دو درجوں کے درمیان واضح انتخاب](/t/url-shot?url=%2F%23%2Ftool%2Fqr-code%3Furl%3Dhttps%3A%2F%2Flolly.tools%26format%3Dpdf%26password%3Ddemo%26options&width=1440&height=900&dpi=192&waitMs=2200&cropSelector=.export-pdfpass&walker=1&format=svg&dark=1&filename=aud-pdf-lock)

- **PDF اوپن-پاس ورڈ** - *Standard* ایک 40-بٹ RC4 رکاوٹ ہے (کہیں بھی کھلتا ہے، لنک میں سفر کر سکتا ہے)؛ *Strong* **AES-256** (PDF 2.0) ہے، ایکسپورٹ کے وقت ٹائپ کیا جاتا ہے اور کبھی لنک میں نہیں ڈالا جاتا۔
- **مقفل ڈاؤن لوڈز** - ایک ZIP، ایک Projects فولڈر یا ایک بیچ رن پورا مقفل ہو سکتا ہے: *Standard* ZipCrypto (کمزور، عالمگیر) یا *Strong* **AES-256** (WinZip AE-2)۔ گہرا دفاع: ایک Strong zip کے اندر کوئی بھی PDF *بھی* الگ سے AES-256 مقفل ہوتی ہے، لہٰذا کھولنے کے بعد بھی مقفل رہتی ہے۔
- **پاس ورڈ سے محفوظ شیئر لنکس** - پوری لنک اسٹیٹ PBKDF2 سے اخذ کردہ کلید کے تحت AES-256 خفیہ کردہ ہوتی ہے؛ صرف سائفر ٹیکسٹ سفر کرتا ہے، پاس ورڈ کبھی لنک میں نہیں ہوتا اور ڈی کرپشن وصول کنندہ کے براؤزر میں ہوتی ہے۔

## ایئر-گیپ کے لیے تیار

ایئر-گیپ ایک **پہلے درجے کی تعیناتی** ہے، کوئی خاص موڈ نہیں - Lolly رینڈر کے وقت بغیر کسی نیٹ ورک کے، ازخود چلتا ہے۔ ویب شیل ایک آف لائن-فرسٹ PWA ہے (سروس ورکر)؛ فونٹس اور WASM ڈیوائس پر محفوظ ہوتے ہیں؛ ٹول اسٹیٹ ہوسٹ بریج کے ذریعے مقامی طور پر محفوظ ہوتی ہے، کبھی `localStorage` میں نہیں۔ ٹول کے نیٹ ورک تک پہنچنے کا تعاون یافتہ طریقہ ایک **allowlisted** `host.net` صلاحیت ہے جسے وہ اپنے مینی فیسٹ میں اعلان کرتا ہے - ایک شیل جو یہ پورا نہیں کر سکتا (یا نہیں کرنا چاہتا) اسے اسٹب کر دیتا ہے۔ یہ ایک نافذ کردہ حد کی بجائے ایک نقل پذیری کا معاہدہ ہے (نیچے ہکس کا نوٹ دیکھیں)، اسی لیے ٹول کوڈ کا جائزہ لینا ہی کنٹرول رہتا ہے - اگرچہ ایک ایئر-گیپڈ ڈیوائس پر ویسے بھی پہنچنے کو کچھ نہیں ہوتا۔ شیلز کو اپنے MDM کے ذریعے ڈیوائسز تک پہنچائیں، یا اپنے نیٹ ورک کے اندر ایک انسٹینس سرو کریں، اور ایک مکمل ایئر-گیپڈ انسٹال بغیر کہیں بھی رابطہ کیے رینڈر، ایکسپورٹ، خفیہ کاری اور اسناد کی تصدیق کرتا ہے۔

## جاننے کے قابل باتیں

چند باتیں جو اسے رول آؤٹ کرنے سے پہلے واضح ہونی چاہییں:

- **سختی جاری ہے۔** کرپٹوگرافی اور پارسرز SUSE کی انٹرپرائز پیمانے کی سختی سے گزر رہے ہیں (اوپر دیکھیں) - آج بذاتِ خود مضبوط ہیں؛ جہاں معاہدہ تصدیق شدہ یقین دہانی چاہے وہاں گہرے دفاع کے طور پر تعینات کریں۔
- **ٹول ہکس سیکیورٹی سینڈ باکس *نہیں* ہیں۔** ٹول کا اختیاری `hooks.js` ہوسٹ بریج انجیکٹ کیے ہوئے چلتا ہے، لیکن ایک براؤزر شیل میں یہ صفحے کے ریلم میں چلتا ہے اور `window`/`document`/`fetch` تک پہنچ *سکتا* ہے۔ ٹول کوڈ کو ویسے ہی سمجھیں جیسے آپ کوئی بھی چلایا جانے والا کوڈ سمجھتے ہیں - اس کا جائزہ لیں۔ یہی وجہ ہے کہ ایک ادارہ جو مشترکہ کیٹلاگ چلاتا ہے وہ اسے Git ریویو کے ذریعے گیٹ کر سکتا ہے؛ بہرحال، صرف وہی ٹولز چلائیں جن کا آپ نے جائزہ لیا ہو جب تک Worker isolation نہیں آتا۔
- **Content Credentials چھیڑ چھاڑ کا پتا دینے والی ہیں۔** یہ چھیڑ چھاڑ کو روکنے کی بجائے اس کی نشاندہی کرتی ہیں - اوپر باہمی تعامل کے نوٹس دیکھیں۔
- **خفیہ کاری کے دو درجے۔** *Standard* لاکس تیز، عالمگیر رکاوٹیں ہیں؛ *Strong* (AES-256) مکمل تحفظ ہے - کسی بھی حساس چیز کے لیے Strong کا انتخاب کریں، یہ نوٹ کرتے ہوئے کہ اسے ایک جدید ریڈر درکار ہے۔

## علیحدہ، یا ایک control plane کے تحت زیرِ انتظام

دو شکلیں، اور آپ ہر deployment کے لیے چنتے ہیں۔ **Standalone ڈیفالٹ ہے اور کسی سرور کی ضرورت نہیں:** Lolly آلے پر ہی render کرتی ہے، ہر producer ایپ کے اندر کام کرتا ہے، اور اوپر بیان کردہ git-as-data حکمرانی مکمل طور پر اختیاری ہے - ایک اکیلی تنظیم اس repo کو بغیر کچھ بھی host کیے چلا سکتی ہے۔ **جب آپ کو تنظیم بھر میں کنٹرول چاہیے، ایک control plane شامل کریں۔** [lolly.work](https://lolly.work) ایک الگ، اوپن سورس (MPL-2.0) سروس ہے جسے آپ خود host کرتے ہیں - یا hosted sandbox پر جانچتے ہیں - جو shell کو لائیو زیرِ انتظام رکھتی ہے: SSO سے مشروط sign-in، feature-flag / export / watermark policy، tool-input overlays، catalog federation، منظوریاں اور ایک hash-chained audit log، یہ سب shell کو یہاں کوئی کوڈ تبدیل کیے بغیر پہنچایا جاتا ہے۔ یہ برانڈ سے غیر متعلق ہے (config کے ساتھ ایک pack mount)، اس repo کے engine اور packs کو بلا ترمیم استعمال کرتی ہے، اور کبھی render راستہ نہیں بنتی: Lolly بذاتِ خود بدستور آلے پر render کرتی ہے۔ OSS = انفرادی آزادی؛ OSS + control plane = تنظیمی آزادی۔
