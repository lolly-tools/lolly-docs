# 面向运维人员的 Lolly

### 一套纵深防御的安全与情报策略 - 恰好也是一个创意生产平台

这是一套零信任的组织免疫系统，包裹在你已有的工作方式之外 - 让团队每天需要的常规创意工作发生在你的边界*之内*，而不是外泄到边界之外。

**这对你意味着什么。** 你将成为那个对既安全*又*受欢迎的东西说“可以”的人。你一举堵上了一个数据外泄漏洞、获得了新能力，还删掉了一条请求队列 - 这种能让你更受欢迎而非更不受欢迎的安全成果并不多见。不会再有法务在凌晨三点打来的电话，只因为受限文件或客户数据流入了某个随意的网页工具；你要应付的 SaaS 供应商、合同和审计也更少了；还有一条完全可复现的审计轨迹，随时可以拿出来回应质询。你会睡得更好，顺带也照亮身边人的几天。

Lolly 绝非二流的创意工具：它把生产级的输出交到每个人手中，其品牌引导式的创作体验也首屈一指。之所以能*安全地*大范围普及，原因在于架构本身：不会有你没主动放上去的内容被上传，每个结果都可复现，每次导出都可以携带多层业界领先的密码学记录。无论一份文档以何种方式送到你桌上，你都能看到它完整的溯源信息、是否被篡改过，以及能否逐像素地重新生成它。

> **目前所处的阶段。** Lolly 的安全特性从设计上就很强，其密码学与文件解析引擎正在经历 SUSE 企业级基础设施加固的过程。下文所述的密封、设备端签名与加密现在就是真实且站得住脚的，并正朝着独立认证不断成熟 - 因此在合同要求经认证的保证时，可在这一过程完成期间将它们作为纵深防御措施来部署。

## 战略优势

常规创意工作通常的完成方式本身就是一个责任风险面：文件被邮寄给外部设计承包商，品牌资产被上传到十几个 SaaS 编辑器，客户数据被粘贴进陌生人的网页工具里，只为“做张快速图表”。这其中每一次都是数据脱离你的掌控。

Lolly 把这一切反过来。那些*引发*外泄的工作 - 语录卡片、本地化横幅、活动徽章、打了码的截图 - 现在都在一个运行于员工自己设备上、针对你的品牌、且没有任何服务器介入的工具中完成。你不是在有风险的工作流之上叠加了一层管控，而是用一个从一开始就不存在外泄路径的工作流取代了它。

- **配置权在你手中。** 引擎和宿主环境都是开源的（MPL-2.0）。你可以叠加自己的身份验证、遥测或 CA；自行托管或不托管；功能和成本完全由你掌控，一切都受 Git 追踪，不会被锁死在某个 SaaS 数据库里。
- **治理可以是数据，而非一块仪表盘。** 当你需要这种控制力时，可以把工具目录作为一个 Git 仓库来管理 - 拉取请求审查就成了品牌审批，拥有完整的审计轨迹，并可以对员工能接触到的每个模板即时回滚。这是一个选项，而非义务，而且只落到一个人的桌面上：创作者完全在应用内工作，把自己做出的东西保存为**会话**，再以分享链接、备份或实时协作的方式传递出去 - 这一切都不需要用到 Git。当某个会话值得成为一个永久的起点时，负责运行部署的人打开该链接，把它的取值记录为品牌包中该工具的一个**模板**并提交。从那时起，它就会出现在该工具的“从模板新建”选择器中，并可通过 `?template=<id>` 深度链接访问。Git 是管理员的锁定步骤，只用一次，创作者永远不需要接触它。参见[采用与治理](/info/adoption-governance.html)。
- **护栏是结构性的。** 品牌约束被硬编码进模板中，而不是作为人们可以无视的指导方针发布出去。错误的输出不是被劝阻 - 而是根本无法表达。

> **你掌管着整场接力。** 创意人员撰写规则，开发者将其规模化，但正是运维人员让这一整套生命周期能够在全组织范围内安全运行 - 同一个能让一名代表在飞机上自助完成工作的工具，也是你可以通过 Git 审查来把关、通过 MDM 来部署、并以密码学方式来验证的工具。参见[一场活动的生命周期](/info/overview.html#the-lifecycle-of-a-campaign)了解这些角色如何叠加发挥作用，以及[采用与治理](/info/adoption-governance.html)了解你要如何治理它。

## 在内容产出激增的同时，删掉请求队列。

Lolly 的一个目标是**分流设计请求**：让常规请求根本无需送达设计师手中，因为需要这份素材的人自己就能在几分钟内正确完成。每一张被分流掉的工单，既是一次生产力上的胜利，也意味着少了一份在人与人之间流转的文件。

Lolly 的设计是为了贴合你的组织实际的运作方式 - 部署它并没有唯一正确的方法：

- **分发部署，而非服务化托管。** 通过你现有的 MDM（Intune、Jamf、Munki……）把 Lolly 分发到各设备上。它以桌面/移动应用或离线 PWA 的形式在本地运行 - 可在任何防火墙之后、任何隔离网络环境中工作，无需维护服务器，更新节奏由 IT 掌控。
- **仅服务化托管。** 在你的网络内（或 VPN 后）运行一个实例；用户通过浏览器访问，无需安装任何东西。发布一次工具，所有人立即都能用上；可搭配你的身份提供方（IdP）实现访问控制。
- **混合模式。** 离线现场工作用本地应用，借用设备则用始终保持最新的浏览器版本 - 两者都指向同一个工具库。

完整的部署模式与管理演示见[部署](/info/deployment.html)和[配置](/info/configuration.html)。

## 防数据外泄实用工具

Lolly 有一类工具 - 隐私类实用工具 - 存在的目的*正是*为了让文件留在边界之内。


- **清除隐藏数据**
 从文档和媒体文件中移除位置信息以及所有隐藏的身份识别信息。

- **Text Helper**  
匿名化、编码、格式化并处理结构化和非结构化文本。

- **Compress PDF**
在设备本地压缩过大的 PDF,这样文件大到无法通过邮件发送时,没有人会去找第三方的“压缩我的 PDF”网站 - 而这恰恰是数据外泄的地方。

这些都是设备本地的转换:你的文件或数据进入,干净的字节输出,**中间没有服务器可供上传**。它们是典型的“把文件上传到陌生人的网站上清理”工具的刻意对立面 - 否则,一位好心的员工往往会转而使用那种工具。

Text Helper 提供的是同样的交易,只不过对象是文本而非文件。它是员工原本会去陌生网站上寻找的那种带标签页的工作台,而且它完全不声明任何输入项,因为它所处理的一切都不会离开页面。

## 确定性与可复现性

每个工具输入都可以表示为一个 URL 参数,相同的输入会生成相同的文件。这对操作者而言有两个结果:

- **URL 本身就是产物。** 提交链接,按需重新生成资源 - 无需向 Git 提交二进制文件,也无需在聊天记录里追“最新版本”。资源和工具 ID 是永久性的约定,因此今天生成的链接以后依然可以解析。
- **CLI 走的是与 GUI 相同的渲染路径**,因此构建流水线和应用永远不会出现偏差。可在构建时以可复现的方式生成 OG 图片、社交卡片和数据可视化图。

Prompt to Image 是确定性最朴素的体现:文本就是全部输入,排版后的图像就是全部输出,相同的文本总是以相同的方式排版。

![Prompt to Image - 一段提示文本排版成一张方形图像,结果中不包含任何输入之外的内容](/t/url-shot?url=%2F%23%2Ftool%2Fprompt-to-image%3Ffull&width=1440&height=900&dpi=192&waitMs=2200&walker=1&format=svg&cropSelector=%23tool-canvas&dark=1&filename=ov2-prompt-to-image)

## 来源与 Content Credentials

![Verify 拖放区接受来自任何来源的任意文件,并且无需网络请求即可读取它](/t/url-shot?url=%2F%23%2Fverify&width=1440&height=900&dpi=192&waitMs=1800&waitSelector=.valid-drop&cropSelector=.valid-drop&format=svg&walker=1&dark=1&filename=aud-verify-drop)

导出的文件可以携带**Content Credentials** - 一份经过签名的 [C2PA](https://c2pa.org) 清单,与文件字节的哈希值绑定。此后对文件的任何改动都会破坏这个签章,因此支持 C2PA 的验证器能够**以密码学方式离线检测篡改**。该凭证是防篡改*可察觉*的:它标记篡改而非阻止篡改,而正是这一点使完全离线验证成为可能。

- **默认开启,设备本地完成。** 签名密钥在设备上生成,不可导出(即使 Lolly 也无法读取),签名过程也在本地完成 - 只有可选的身份*注册*才会连接网络。
- **信任等级。** 未注册的导出文件格式正确,但以匿名方式签名(`untrusted`)。注册一个**已验证身份**(由 Lolly CA 签发的短期证书,与邮箱绑定)后,固定信任 Lolly 根证书的验证器会报告 `trusted` 以及签署者的邮箱。可信时间戳机构和第三方验证器认证(C2PA 一致性)已在路线图中。每个等级都是明确的,文件只会声明它能够证明的信任程度。
- **凭证有效期**由操作者/用户在签名时决定:7 / 30 / 90 / 365 天,默认 30 天。
- **Lolly Imprint。** 一个**默认开启**的第二重互补信号:一种烘焙进光栅导出文件(以及 PDF/PPTX 内由 Lolly 渲染的光栅图,但绝不包括用户自行嵌入的图片)中的隐形像素水印。凭证会在容器发生任何改动时失效,而 Imprint 能在重新保存或截图后依然存活 - 是一种持久的“这些像素经过 Lolly 处理”的提示,只表明存在与否,不含任何个人数据。它属于隐蔽式安全手段,而非强化防御,是对凭证的补充而非替代。`imprint=0` 可以关闭它。
- **持久 Content Credentials(可选开启)。** 光栅导出文件还可以额外携带一个隐形的*持久*标记,其中编码了一个软绑定标识符,使得即便社交平台上传或重新保存清除了文件的元数据,C2PA 凭证依然可以被恢复 - 这正是普通凭证会丢失的情形。该功能仅适用于光栅图,且需要一次神经网络编码处理,因此默认关闭(`durable=1` 可开启)。Lolly 目前可以在 `/verify` 上离线识别自己的持久标记;等业界的软绑定解析方案就绪后,第三方工具(例如 Adobe)的恢复能力也会随之支持。
- **验证在设备本地完成。** 将任意文件拖放到 `/verify`(或运行 `lolly validate <file>`)即可获得一份离线报告,说明该文件是否确实由 Lolly 制作且此后未被更改。网页版 Verify 视图还会标记 AI 生成内容、检测 Lolly Imprint、验证 **SEAL** 签名(一种字节级签名 - 零网络请求:引擎接受一个*注入式*的 DNS 密钥解析器,而目前没有任何 shell 注入这样的解析器,因此携带自身内联 `pk=` 密钥的记录可以完全离线验证,而依赖 DNS 的记录则会报告 "no key resolver and no inline key" 而不会发起外部请求 - 参见 `engine/src/seal.ts` 中的 `SealPublicKeyResolver`),还可以选择深度扫描第三方像素水印(需一次性下载设备本地模型)并揭示隐藏数据 - 这一切都无需上传文件。参见 [Content Credentials Identity](/info/content-credentials-identity.html)。

> **互操作性说明。** Lolly 目前可以离线验证自身的凭证以及许多第三方凭证,包括读取其他生产者签发的 C2PA 声明 **v2** 清单。有两种容器仍在推进中,原因都是 C2PA 尚未为它们制定标准化映射,因此 Lolly 把凭证放在自己定义的位置,也由 Lolly 的验证器负责读回:**WebM**(清单以 Matroska 附件形式携带)和 **Ogg/Opus**(OpusTags 注释头中的 `C2PA=` 字段,该字节范围会被排除在绑定之外,以便音频哈希值保持一致)。其余格式都按规范加盖印记 - 第三方工具可以直接验证 Lolly 输出的 MP4、M4A、MP3、WAV、PNG、JPEG 和 PDF。两种映射均参见 `engine/src/c2pa-containers.ts`;一旦标准落定,它们会与标准趋同。

## 加密与密码保护

对于必须加锁传输的文件,一切都在设备本地完成:

![导出面板中的加锁卡片:一个密码输入框,以及在两个等级之间的明确选择](/t/url-shot?url=%2F%23%2Ftool%2Fqr-code%3Furl%3Dhttps%3A%2F%2Flolly.tools%26format%3Dpdf%26password%3Ddemo%26options&width=1440&height=900&dpi=192&waitMs=2200&cropSelector=.export-pdfpass&walker=1&format=svg&dark=1&filename=aud-pdf-lock)

- **PDF 打开密码** - *Standard* 是 40 位 RC4 级别的威慑性保护(到处都能打开,可以随链接一起传播);*Strong* 是 **AES-256**(PDF 2.0),在导出时输入,绝不会出现在链接中。
- **加锁下载** - 一个 ZIP、一个 Projects 文件夹或一次批处理运行可以整体加锁:*Standard* 使用 ZipCrypto(强度较弱,但通用性好),或 *Strong* 使用 **AES-256**(WinZip AE-2)。纵深防御:Strong 压缩包内的任何 PDF *也* 会单独用 AES-256 加锁,因此解压后依然保持加锁状态。
- **密码保护的分享链接** - 整个链接状态都使用基于 PBKDF2 派生密钥的 AES-256 加密;传输的只有密文,密码永远不会出现在链接中,解密在接收者的浏览器中完成。

## 气隙就绪

气隙(air-gap)是一种**一等部署方式**,而非特殊模式 - Lolly 开箱即用,在渲染时无需任何网络。Web shell 是一个离线优先的 PWA(service worker);字体和 WASM 都存储在设备本地;工具状态通过 host bridge 在本地持久化,绝不使用 `localStorage`。工具能够访问网络的受支持方式,是它在清单中声明的**白名单化**的 `host.net` 能力 - 无法(或不愿)满足该能力的 shell 会将其存根化。这是一种可移植性约定,而非强制边界(参见下方关于 hooks 的说明),这也是为什么审查工具代码依然是关键控制手段 - 不过在气隙设备上,原本也无处可访问。通过你的 MDM 将各个 shell 分发到设备上,或者在你的网络内部提供一个实例,一个完全气隙化的安装就能渲染、导出、加密并验证凭证,而没有任何东西可以回传。

## 值得了解

在你部署之前,有几件事值得先弄清楚:

- **加固工作正在进行中。** 加密和解析器代码正在经历 SUSE 企业级规模的加固(见上文) - 目前的设计已经足够稳固;若合同要求经过认证的保证,请将其作为纵深防御的一部分部署。
- **工具 hooks *不是*安全沙箱。** 工具可选的 `hooks.js` 会在注入 host bridge 的情况下运行,但在浏览器 shell 中它是在页面的运行环境里执行的,*可以*访问 `window`/`document`/`fetch`。对待工具代码要像对待你运行的任何代码一样 - 审查它。这也是为什么运行共享目录的组织可以通过 Git 审查来把关;无论哪种方式,在 Worker 隔离上线之前,都只应运行你已审查过的工具。
- **Content Credentials 是防篡改可察觉的。** 它们检测篡改而非阻止篡改 - 参见上文的互操作性说明。
- **两个加密等级。** *Standard* 加锁是快速、通用的威慑手段;*Strong*(AES-256)是完整保护 - 对任何敏感内容都应选用 Strong,但要注意它需要现代的阅读器支持。
