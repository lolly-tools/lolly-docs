# 給維運者的 Lolly

### 一套縱深防禦的安全與情報策略 - 恰好也是一個創意生產平台

這是包裹在你既有工作之外的零信任組織免疫系統 - 讓團隊每天都需要的例行創意工作發生在你的邊界*之內*,而不是外洩出去。

**這對你有什麼好處。** 你可以成為那個對既安全*又*受歡迎的方案點頭的人。你一次動作就堵住外洩漏洞、獲得能力,還刪掉一條請求佇列 - 這種安全性上的勝利很罕見,能讓你更受歡迎,而不是更不受歡迎。不會再有機密檔案或客戶資料誤入某個隨機網路工具而在半夜三點接到法務的電話;要應付的 SaaS 供應商、合約和稽核也變少;還有一份完全可重現的稽核軌跡,在有人問起時可以直接拿出來。你能睡得更安穩,也能順帶讓幾天過得更輕鬆。

Lolly 絕非次等的創意工具:它把生產品質的產出交到每個人手中,而且品牌導向的創作體驗無人能及。之所以能*安全地*廣泛發放,是因為架構本身:沒有東西會在你不知情的情況下上傳,每個結果都可重現,而且每次匯出都可以攜帶多層業界領先的加密紀錄。無論一份文件是如何送到你桌上的,你都能看到它完整的來源、是否遭到竄改,以及你是否能像素級精確地重新產生它。

> **目前的進度。** Lolly 的安全特性在設計上就很紮實,其加密與檔案解析引擎正經歷 SUSE 企業級基礎架構的強化過程。以下的密封、裝置端簽署與加密現在就是真實可靠的,並正朝獨立驗證邁進 - 因此若合約要求經認證的保證,可在該流程完成之際將它們作為縱深防禦的一環部署。

## 策略優勢

一般完成例行創意工作的方式本身就是一個風險面:檔案透過電子郵件寄給外部設計承包商、品牌資產上傳到十幾個 SaaS 編輯器、客戶資料貼到陌生人的網路工具裡「只是想快速做張圖」。以上每一項都是資料離開你的掌控範圍。

Lolly 反其道而行。原本*導致*那些外洩的工作 - 引言卡、在地化橫幅、活動識別證、遮蔽過的螢幕截圖 - 現在改在一個於員工自己裝置上執行、對接你的品牌、且中間沒有伺服器的工具上完成。你並不是在有風險的工作流程上加了一層控管;你是用一個從一開始就沒有外洩路徑的工作流程,取代了那個有風險的工作流程。

- **設定由你掌控。** 引擎與 shell 皆為開放原始碼(MPL-2.0)。你可以疊加自己的驗證機制、遙測或 CA;可以自行架設,也可以不架設;你握有完整的功能與成本控制權,以 git 追蹤,而不是被鎖在某個 SaaS 資料庫裡。
- **治理可以是資料,而不是儀表板。** 當你想要那種控管時,可以把工具目錄當作一個 Git 倉庫來管理 - 拉取請求審核就成了品牌核准,擁有完整的稽核軌跡,並可即時回復你的員工能接觸到的每一份模板。這是一個選項,不是義務,而且只落在一張辦公桌上:創作者完全在應用程式內工作,把成果存成一個**工作階段**,並以分享連結、備份或即時協作的方式傳遞 - 這些都不需要用到 git。當其中某個工作階段值得成為永久的起點時,負責部署的人就開啟連結、把它的值記錄為品牌套件中該工具的**模板**並提交。從此以後,它就會出現在該工具的「從模板新增」選單中,也能以 `?template=<id>` 的形式深層連結。Git 是管理員的鎖定步驟,只用一次,創作者永遠不需要碰。詳見[採用與治理](/info/adoption-governance.html)。
- **護欄是結構性的。** 品牌限制是硬寫進模板裡的,而不是發布成人們可以無視的指引。錯誤的產出不是被勸阻 - 而是根本無法呈現。

> **你統管整條接力賽。** 創意人員撰寫規則,開發人員將其規模化,但讓這整個生命週期能在全組織範圍安全運作的人,是維運者 - 同一個能讓業務代表在飛機上自助服務的工具,你也能透過 Git 審核來把關、透過你的 MDM 部署,並以密碼學方式驗證。想了解各角色如何相互加乘,見[一次行銷活動的生命週期](/info/overview.html#the-lifecycle-of-a-campaign);想了解你如何治理它,見[採用與治理](/info/adoption-governance.html)。

## 在內容持續增長的同時,刪掉請求佇列。

Lolly 的目標之一是**設計請求分流**:讓例行請求根本不需要送到設計師手上,因為需要素材的人自己就能在幾分鐘內正確做出來。每一張被分流掉的工單,既是生產力上的勝利,也少了一個經手檔案的環節。

Lolly 的設計是為了配合你組織實際的運作方式 - 部署方式沒有單一正確答案:

- **部署,而非架設服務。** 透過你既有的 MDM(Intune、Jamf、Munki……)將 Lolly 送到裝置上。它以桌面/行動應用程式或離線 PWA 的形式在本機執行 - 可在任何防火牆之後、任何氣隙環境中運作,不需要維護伺服器,更新節奏由 IT 掌控。
- **只架設服務。** 在你的網路內(或 VPN 之後)執行一個實例;使用者透過瀏覽器連線,不需要安裝任何東西。發布一次工具,每個人立即都能使用;搭配你的 IdP 進行存取控管。
- **混合式。** 離線的現場工作使用本機應用程式,借用機器則使用永遠最新的瀏覽器版本 - 兩者都指向同一個工具庫。

完整的部署模式與管理演練,詳見[部署](/info/deployment.html)與[設定](/info/configuration.html)。

## 反外洩公用工具

有一類 Lolly 工具 - 隱私公用工具 - 存在的目的*就是*把檔案留在邊界之內。


- **移除隱藏資料**
 移除文件與媒體檔案中的位置資訊及所有隱藏的識別資訊。

- **Text Helper**  
匿名化、編碼、格式化並處理結構化與非結構化文字。 

- **Compress PDF**
在裝置端壓縮過大的 PDF，讓使用者不會在檔案大到寄不出去時，求助於第三方的「幫我壓縮 PDF」網站 - 而這正是資料外洩的破口。 

這些全都是裝置端轉換：你的檔案或資料進去，乾淨的位元組出來，而且**沒有伺服器可以上傳**。它們刻意與典型的「把檔案上傳到陌生網站來清理」工具背道而馳 - 那正是善意的員工原本會求助的做法。

## 確定性與可重現性

每個工具輸入都能以 URL 參數表示，相同的輸入會產生相同的檔案。這對操作者而言有兩個結果：

- **URL 就是產出物。** 提交連結，需要時再按需重新產生資產 - 不必把二進位檔案簽入 Git，也不必在聊天記錄裡追「最新版本」。資產與工具 ID 是永久性的約定，因此今天產生的連結，日後依然能正確解析。
- **CLI 走的是與 GUI 相同的渲染路徑**，因此建置流程與應用程式永遠不會分歧。可以在建置時可重現地產生 OG 圖片、社群卡片與資料視覺化圖表。

Prompt to Image 是確定性最單純的體現：文字就是全部的輸入，排版好的圖片就是全部的輸出，相同的文字永遠會排出相同的結果。

![Prompt to Image - 一段提示文字排版成正方形圖片，結果中沒有任何內容不是來自輸入](/t/url-shot?url=%2F%23%2Ftool%2Fprompt-to-image%3Ffull&width=1440&height=900&dpi=192&waitMs=2200&walker=1&format=svg&cropSelector=%23tool-canvas&dark=1&filename=ov2-prompt-to-image)

## 來源與 Content Credentials

![Verify 的拖放區接受任何來源的任何檔案，且讀取過程不會發出任何網路請求](/t/url-shot?url=%2F%23%2Fverify&width=1440&height=900&dpi=192&waitMs=1800&waitSelector=.valid-drop&cropSelector=.valid-drop&format=svg&walker=1&dark=1&filename=aud-verify-drop)

匯出檔案可以附帶**Content Credentials** - 一份已簽署、與檔案位元組雜湊值繫結的 [C2PA](https://c2pa.org) 資訊清單。檔案之後只要有任何更動，都會破壞這份封籤，因此支援 C2PA 的驗證工具能夠**以密碼學方式離線偵測遭竄改**。這份憑證是竄改-*可偵測*的：它標示竄改，而非防止竄改，而這正是能夠完全離線驗證的原因所在。

- **預設開啟，裝置端運作。** 簽署金鑰在裝置上產生，無法匯出（連 Lolly 也讀不到），簽署也在本機完成 - 只有選擇性的身分*註冊*才會連上網路。
- **信任層級。** 未註冊身分的匯出檔案格式完整，但屬於匿名簽署（`untrusted`）。註冊**已驗證身分**（來自 Lolly CA 的短效憑證，與電子郵件綁定）後，釘選 Lolly 根憑證的驗證工具會回報 `trusted` 加上簽署者的電子郵件。可信賴時間戳記機構與第三方驗證器綠燈認證（C2PA 相容性）已列入路線圖。每個層級都是明確標示的，檔案只會宣稱它能證明的信任程度。
- **憑證有效期限**由操作者/使用者在簽署當下決定：7 / 30 / 90 / 365 天，預設為 30 天。
- **The Lolly Imprint。** 第二個互補訊號，**預設開啟**：烘焙進點陣匯出檔案中的隱形像素浮水印（也包括 PDF/PPTX 中由 Lolly 渲染的點陣圖，但絕不包含使用者自行內嵌的圖片）。憑證會因容器格式的任何變動而失效，Imprint 卻能撐過重新儲存或截圖 - 這是一個持久性的「這些像素曾經過 Lolly」提示，僅表示存在與否，不含任何個人資料。這屬於隱蔽式安全，而非強化防禦，用來補強憑證，而非取代憑證。`imprint=0` 可選擇退出。
- **持久性 Content Credentials（選擇加入）。** 點陣匯出檔案還可以額外攜帶一個隱形的*持久性*標記，其中編碼了一組軟綁定識別碼，因此即使社群平台上傳或重新儲存已經清除了檔案的中繼資料 - 也就是一般憑證會遺失的情況 - C2PA 憑證仍可被復原。此功能僅限點陣圖，且需要一次神經網路編碼運算，因此預設關閉（`durable=1` 可開啟）。Lolly 目前能在 `/verify` 上離線辨識自己的持久性標記；等業界的軟綁定解析機制就緒後，第三方工具（例如 Adobe）也將能夠復原。
- **驗證在裝置端進行。** 將任何檔案拖放到 `/verify`（或執行 `lolly validate <file>`），即可取得該檔案是否真的由 Lolly 產生、且之後未經更動的離線報告。網頁版 Verify 檢視畫面還會標示 AI 生成內容、偵測 Lolly Imprint、驗證 **SEAL** 簽章（一種位元組層級的簽章 - 且零網路請求：引擎採用*注入式*的 DNS 金鑰解析器，而目前沒有任何 shell 會注入解析器，因此帶有內嵌 `pk=` 金鑰的紀錄能完全離線驗證，而依賴 DNS 金鑰的紀錄則會回報「沒有金鑰解析器，也沒有內嵌金鑰」，而不會嘗試連線 - 詳見 `engine/src/seal.ts` 中的 `SealPublicKeyResolver`），也可選擇深度掃描第三方像素浮水印（需一次性下載裝置端模型）並揭露隱藏資料 - 這一切都不需要上傳檔案。詳見 [Content Credentials Identity](/info/content-credentials-identity.html)。

> **互通性說明。** Lolly 目前能離線驗證自己的憑證，也能驗證許多第三方憑證，包括讀取其他產製工具的 C2PA claim **v2** 資訊清單。有兩種容器格式仍在進行中，原因都是 C2PA 目前尚未針對它們制定標準化的對應方式，因此 Lolly 會把憑證放在自己定義的位置，並由 Lolly 自己的驗證工具讀回：**WebM**（資訊清單以 Matroska 附件形式搭載）與 **Ogg/Opus**（OpusTags 註解標頭中的 `C2PA=` 欄位，且該位元組範圍會排除在綁定範圍之外，讓音訊仍能雜湊出相同的結果）。其餘格式一律照規格標記 - 第三方工具開箱即可驗證 Lolly 輸出的 MP4、M4A、MP3、WAV、PNG、JPEG 與 PDF。兩種對應方式詳見 `engine/src/c2pa-containers.ts`；等業界標準底定後，兩者將會趨於一致。

## 加密與密碼保護

對於必須以鎖定狀態傳輸的檔案，一切都在裝置端完成：

![匯出面板中的鎖定卡片：一個密碼欄位，以及在兩個層級之間明確選擇的選項](/t/url-shot?url=%2F%23%2Ftool%2Fqr-code%3Furl%3Dhttps%3A%2F%2Flolly.tools%26format%3Dpdf%26password%3Ddemo%26options&width=1440&height=900&dpi=192&waitMs=2200&cropSelector=.export-pdfpass&walker=1&format=svg&dark=1&filename=aud-pdf-lock)

- **PDF 開啟密碼** - *Standard（標準）* 是 40 位元 RC4 的基本防護（到處都能開啟，可能隨連結一起傳送）；*Strong（強）* 則是 **AES-256**（PDF 2.0），在匯出時輸入，絕不會出現在連結中。
- **鎖定下載內容** - ZIP、Projects 資料夾或批次執行結果都可以整份鎖定：*Standard* 使用 ZipCrypto（較弱但通用），或 *Strong* 使用 **AES-256**（WinZip AE-2）。深度防禦：在 Strong 壓縮檔中的任何 PDF，也*同時*個別以 AES-256 鎖定，解壓後依然維持鎖定狀態。
- **設有密碼的分享連結** - 整個連結狀態會以 PBKDF2 衍生金鑰進行 AES-256 加密；傳輸的只有密文，密碼絕不會出現在連結中，解密則在收件者的瀏覽器內進行。

## 支援氣隙隔離環境

氣隙（air-gap）是**一等公民的部署方式**，不是特殊模式 - Lolly 開箱即可在渲染時完全不連網運作。網頁版 shell 是離線優先的 PWA（service worker）；字型與 WASM 都儲存在裝置端；工具狀態透過 host bridge 儲存在本機，絕不使用 `localStorage`。工具要連上網路的唯一支援方式，是在其資訊清單中宣告的**白名單制** `host.net` 能力 - 無法（或不願）提供此能力的 shell 會回傳空實作。這是一份可攜性約定，而非強制邊界（見下方 hooks 說明），因此審查工具程式碼依然是主要控管手段 - 不過在氣隙裝置上，本來就無處可連。透過你的 MDM 將 shell 部署到裝置上，或在你的網路內架設一個執行個體，一套完全氣隙化的安裝即可渲染、匯出、加密並驗證憑證，完全沒有任何對外回報的管道。

## 你應該知道的事

在推出之前，有幾件事值得先弄清楚：

- **強化作業進行中。** 密碼學與解析器目前正在接受 SUSE 企業級規模的強化（見上文）- 就目前設計而言已經很穩固；若合約要求通過認證的保證，請將其部署為深度防禦的一環。
- **工具 hooks *不是*安全沙箱。** 工具選用的 `hooks.js` 會在注入 host bridge 的情況下執行，但在瀏覽器 shell 中，它是在頁面的執行環境中運作，*可以*存取 `window`/`document`/`fetch`。請以看待任何你執行的程式碼的方式看待工具程式碼 - 審查它。這正是為何執行共用目錄的組織可以透過 Git 審查來把關；不論如何，在 Worker 隔離機制上線之前，只執行你已審查過的工具。
- **Content Credentials 是防竄改可偵測的。** 它們偵測變動而非防止變動 - 詳見上方的互通性說明。
- **兩種加密層級。** *Standard* 鎖定是快速、通用的基本防護；*Strong*（AES-256）則是完整防護 - 任何敏感內容都應選用 Strong，並注意它需要較新版的閱讀工具。
